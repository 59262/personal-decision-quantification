# 归档与纠错流程

仅在日记原文归档、正式日提交、批量格式统一或同日异本纠错时读取本文件。普通草稿转写不需要加载。

## 1. 不变量

1. 原始字幕、文字日记、桌面报告和模板母版默认只读。
2. 日期依据顺序为：用户明确确认 > 正文日期与星期线索 > 文件名 > 文件元数据。
3. 原文归档、结构化日提交和AI分析是不同数据层；本Skill只在前两层通过门禁后交接分析，不复制或替代现行AI分析规则。
4. 正式目标存在时必须先算SHA-256，不能凭文件名、大小或修改时间判断相同。
5. 哈希相同可以复用；哈希不同必须停止并说明冲突，除非用户随后明确授权纠错。
6. 用户自填字段没有内容时保持空白，不能为了通过完整性检查而补写“未知”或勾选“不确定”。

## 2. 日记原文归档

### 2.1 目标

- 目录：`01.原始数据记录/03_事件数据/日记原文模块/`
- 文件名：`M月D日日记.原扩展名`
- 内容：源文件字节级副本，不修正字幕、错词、时间码或编码。

若文件名日期与用户确认日期不同，目标按确认日期命名，源文件不重命名。例如源文件为`8月20日.srt`，用户确认内容属于8月19日，则目标为`8月19日日记.srt`。

### 2.2 门禁

1. 记录源路径、扩展名、长度和SHA-256。
2. 检查目标是否存在。
3. 目标不存在：复制后再次计算目标SHA-256；必须与源一致。
4. 目标存在且哈希相同：复用，不能重复创建副本。
5. 目标存在且哈希不同：停止，不覆盖、不自动改名为“副本”。向用户报告冲突。

## 3. 正式日提交

### 3.1 写入前

1. 用户已确认事实内容，或明确要求把已自行填写的报告保存为正式提交。
2. 工作副本已通过格式和事实边界检查。
3. 正式目标为`01.原始数据记录/03_事件数据/提交模块/日提交/日期：YYYY年M月D日.md`。
4. 顶部只保留一条作为元数据生效的独立归属标签行：`#提交内容 #01原始数据记录 [[00_提交模块说明]]`。填写原则中引用同一字符串的说明文字不计作第二条元数据标签。
5. 所有新增双链均能解析到唯一真实目标。

### 3.2 写入与验证

1. 目标不存在时，将已确认工作副本复制到正式目标。
2. 复制后比较工作副本和正式目标SHA-256。
3. 检查正文日期、星期、填写时间、时间线覆盖、非标准复选框和互斥选项。
4. 记录仍然缺失的必填项；没有证据时允许保留空白，不推测补写。
5. 删除只由本次任务创建的临时工作目录；不得删除用户源文件。

## 4. 多日报告格式统一

### 4.1 允许修改

- `[√]`、`[ √]`、`[√ ]`统一为`[x]`，`[]`统一为`[ ]`。
- 用户已填写值两侧的占位下划线可以清理，例如`_4__`变为`4`；纯空字段`___`保留。
- `本次填写时间`规范为`HH:MM`；若用户把日期和时间同时写入，只保留该字段要求的时刻。
- 时间线覆盖统一为模板现行格式，并保留“入睡”与“准备睡觉”的事实差别。
- 标题、YAML、0—11节顺序、表格和Obsidian标记与现行模板对齐。

### 4.2 禁止修改

- 不因统一格式而改变日期、任务对象、决策选项、完成状态、状态评分或用户解释。
- 不把合法展开的信息2、D2或T2压回空模板。
- 不把旧报告重新分析成新的事实版本。
- 不用批量替换覆盖需要逐日判断的日期、星期和时间线。

## 5. 同日异本纠错

### 5.1 授权门禁

正式目标与当前确认版本哈希不同：

1. 读取两份文件的关键字段，指出至少一项用户能理解的差异，如日期、星期、时间线、决策或状态不同。
2. 明确说明现行规则禁止静默覆盖。
3. 询问用户是否授权：保留旧证据、建立恢复包、再替换正式版本。
4. 没有明确肯定答复时停止。多日报告中不得悄悄跳过冲突日期后声称全部完成。

### 5.2 恢复包

获得授权后，在任何覆盖前执行：

1. 精确列出将被替换的正式文件及当前SHA-256。
2. 在临时目录构造恢复包内容：

```text
旧归档/
    日期：YYYY年M月D日.md
恢复说明.md
manifest_sha256.txt
```

3. `manifest_sha256.txt`至少登记所有旧归档文件和恢复说明的SHA-256。
4. ZIP保存到`01.原始数据记录/99_系统演化档案/99_维护备份/`；文件名应包含范围、用途和日期。
5. 完整读取ZIP的每个条目，再按清单逐文件计算SHA-256。任何条目缺失、不可读或哈希不一致都必须停止覆盖。
6. 档案层只长期保存验证过的ZIP和对应记录，不展开保存普通用户日记副本。

### 5.3 替换与竞争条件复检

1. 正式写入前再次计算旧目标SHA-256，必须与刚刚备份的值相同；若变化，停止并重新审计。
2. 只替换用户明确授权的日期；首次归档的日期可以新增。
3. 每份新正式文件写入后，比较确认工作副本与正式文件SHA-256。
4. 不修改桌面源文件、原始SRT或模板母版。

### 5.4 纠错记录

同日生成维护记录，至少包含：

- 用户授权时间与纠错原因；
- 用户提供源路径及源SHA-256；
- 纠错前正式文件路径及旧SHA-256；
- 恢复包路径、ZIP SHA-256、条目数和验证结果；
- 允许的格式变更范围；
- 纠错后正式路径及新SHA-256；
- 源文件未修改声明和单文件回滚方法。

将恢复包和记录登记到`99_系统演化档案/99_维护备份/备份说明.md`。普通日提交纠错不自动改变系统版本，也不追加系统规则变更；只有模板、Skill或规则本身发生变化时才进入系统更新流程。

## 6. 日期校正级联与日分析交接

### 6.1 日期锁定

在创建任何目标文件前，先形成内部日期锁：

```text
event_date: YYYY-MM-DD
date_basis: user_confirmation | body_date | filename | metadata
```

- 用户明确确认优先级最高。
- 源文件夹名、源文件名和文件修改日期只能提供线索。
- 文件名与用户确认冲突时，原文件保持不变，归档目标按`event_date`命名。

### 6.2 用户校正后的依赖图

用户明确校正日期后，不能只改正文日期。按顺序重检：

```text
event_date
→ 星期
→ 工作副本文件名
→ 原文归档文件名
→ 正式日提交文件名
→ 前一日及昨日闭环
→ 下一日及明日行动桥
→ 日分析文件名、标题、窗口和来源双链
→ 本次任务创建的旧日期文件与旧日期引用
```

正文、文件名和派生分析全部一致后，日期修正才算完成。旧日期只允许出现在明确的数据质量修正记录中，不能继续作为运行路径或来源双链。

### 6.3 两类日期纠错

**本轮AI误归档回退**仅在以下条件全部满足时使用：

1. 错误文件由当前任务创建，不是用户原有文件；
2. 用户在同一工作流程中明确给出正确日期；
3. 正确日期的目标文件不存在；
4. 错误文件自创建后没有被外部修改；
5. 先检查工作副本与正式文件哈希、同名分析和全部相关目标；
6. 更正后检查错误日期文件为0、运行双链残留为0，并在分析的数据质量区保留校正来源。

满足这些条件时，可以把本轮创建的错误日期工作副本、正式提交和派生分析整体更正到正确日期。不得删除或改名用户提供的源文件。

**已稳定正式记录纠错**适用于任务开始前已存在、已经被后续报告引用、无法证明仅由本轮创建或校正目标发生冲突的文件。此时必须走第5节同日异本纠错及系统数据完整性流程；没有授权和恢复包时停止。

### 6.4 日分析交接门禁

用户明确要求日分析时：

1. 本轮提供原文且进入完整流程时，原文归档源—目标SHA-256先一致。
2. 最终工作副本—正式日提交SHA-256再一致。
3. 读取现行智能体执行Skill、入口登记的AI分析规则和Obsidian规范。
4. 交接单至少包含：`event_date`、正式提交路径、素材类型、日期修正记录、时间边界、用户自填空白和字段语义错位。
5. 正式分析只能引用正式日提交及实际读取的近日报告；不得引用桌面模板或待确认草稿作为正式来源。
6. 同日日分析已存在且内容不同则停止；不得把“日期校正”当作普通格式替换静默覆盖稳定分析。

## 7. 交付前验证

- [ ] 日期、星期和文件名一致，日期冲突有用户确认依据
- [ ] 已保存内部`event_date`和`date_basis`，日期校正的前后日依赖已重算
- [ ] 三类数据层的目标目录没有混用
- [ ] 原文与目标、工作副本与日提交的SHA-256分别匹配
- [ ] 标准提交标记恰好存在一条
- [ ] 归属标签按独立元数据行计数，未把填写原则中的说明文字误判为重复标签
- [ ] 非标准复选框为0，互斥选项没有多选
- [ ] 用户自填字段未被代填
- [ ] 用户内容与字段语义不一致时只做数据质量标注，未擅自迁移
- [ ] 新增双链断链和歧义为0
- [ ] 纠错恢复包逐条目可读且清单验证失败数为0
- [ ] 纠错记录的新旧哈希、ZIP哈希和恢复范围完整
- [ ] 临时目录已清理，用户源文件和模板母版哈希未变化
- [ ] 需要日分析时，原文和正式提交门禁先通过，分析目标无冲突且来源双链指向正式提交
