#全系统调度 #skill

# Personal System Orchestrator v1.8.0

本Skill是`E:/个人事件量化系统/`唯一面向跨子系统任务的总调度。它负责识别任务范围、选择起点、调用01／H1／02／03执行器、管理停点、核对交接契约和汇总阶段状态；各层事实、Schema和分析规则仍由各自唯一权威定义。

完整执行或跨层续跑前，读取[阶段交接契约](references/stage-contracts.md)。系统更新任务改读[系统更新契约](references/system-update-contract.md)，并同时服从相应子系统的版本治理文件。

## 1. 唯一调度关系

```text
用户／根级全系统入口
  → personal-system-orchestrator（全系统唯一总调度）
      ├─ 01：personal-event-system-orchestrator
      │    └─ diary-transcription等01内部组件
      ├─ H1：personal-health-layer
      │    └─ E:/个人事件量化系统/H1.个人健康层/health-runtime/ 的导入、聚合、报告程序；旧 E:/个人健康层/ 仅为迁移前只读备份，不再同步
      ├─ 02：daily-decision-training-pipeline
      │    └─ 02内部筛选、闭环和构建组件
      └─ 03：decision-state-snapshot
```

01、H1、02、03的Skill都是子系统执行器或组件。它们可以完成本层工作，但不得自行决定跨入下一层，也不得把本层完成表示为全系统完成。H1是横向层，不改变01—08主链编号。

## 2. 请求路由

| 用户目标 | 默认范围 |
|---|---|
| 日记转写、日报归档、D/W/M分析 | 调用01；D/W/M按H1登记读取可用健康资料，不自动进入02 |
| 健康数据导入、健康日报或补算 | 调用H1；需要联合分析时核对01正式日报与D分析 |
| 数据筛查、事件提取、最终日报或派生构建 | 核对01正式输入后调用02 |
| 状态、情绪或选择前状态快照 | 核对02正式Decision后调用03 |
| “完整流程”“从原始数据一直处理到状态／情绪” | 按G0—G5推进，并运行非阻塞H0—H5；遇到用户确认或主链阻断即合法暂停 |
| “继续” | 从最近一个有文件、哈希和状态证据的阶段恢复，不重做已验证阶段 |
| 根据近期数据更新模板、规则或Skill | 进入U0—U6更新路线；不得与G0—G5日报生产混跑 |

只执行用户请求覆盖的范围。统一入口不等于后台常驻自动执行，也不等于可以跳过用户确认、同日冲突或来源变化门禁。

### 2.1 近期执行固定规则

以下规则来自2026-10-20—2026-10-22连续执行，优先于旧的经验性做法：

1. 先做日期门禁。比较用户指定日期、文件名／文件夹日期和转写中的时间线锚点。三者冲突时，G0只建立带`date_conflict=true`的候选草稿并暂停；用户裁决前不得创建正式日提交、02记录、03快照或H4联合报告。
2. “已完成填写”只触发重新读取工作副本。重新读取后，已选字段进入正式输入，未勾选可选字段按`unknown`保留；不得因为用户说已完成就把空白解释成“无”，也不得重复索要已经存在的内容。
3. 工作副本的复选框可以兼容读取`[x]`、`[√]`和带空格的变体；所有正式输出统一写成`[x]`／`[ ]`。
4. 设备只能直接回填客观数据和用户在日记中明确说出的原话。Apple Health不得换算或推断心情、睡眠质量评分、精力、压力、动机、疼痛、困倦或启动阻力；“睡眠约60分”只有在用户明确确认量表口径时才进入评分字段。
5. AI可以判断中心主轴。依据当天实际行动密度、持续时间、决策对象和生活安排；情绪主题可以单独分析，不自动替代执行主轴。
6. 完整Apple Health导出先记录哈希，再导入并只筛选目标日期。新导出可能刷新旧日汇总；未经明确补算请求，不重生成已登记历史日报。发现旧日汇总变化时标为`source_changed`，不静默覆盖H1登记。
7. 健康目录不可写时，H1进入`pending_permission`并返回缺少权限；G主链仍可继续。派生构建脚本在Windows PowerShell报`SHA256.HashData`错误时，切换到`pwsh`并记录运行时版本。
8. 健康、选择与生活关联每天固定输出健康在前、生活／选择在前、同日共现三类候选，带证据等级和反证；少于14个有效健康日时只做观察，不做个人基线或因果判断。

### 2.2 单次日记运行顺序

`识别输入 → 日期门禁 → 候选模板 → 重读已填写副本 → 01正式归档与D分析 → H1按日期筛选 → 02筛查 → 03仅处理真实Decision → 哈希／登记审计`。

健康导入、健康报告和关联分析是横向分支；它们不改变主链顺序，也不为缺少健康数据制造暂停理由。

## 3. 全局状态机

| 状态 | 含义 | 进入下一状态的门禁 |
|---|---|---|
| `G0 input_received` | 收到SRT、文字日记、已填日报或已存在日期 | 真实日期、输入类型、任务终点和现有阶段可判断；日期冲突必须先裁决 |
| `G1 raw_draft` | 01形成结构化草稿 | 主观字段未被AI代填；用户确认草稿 |
| `G2 raw_and_analysis_ready` | 01正式日提交与同日D分析就绪 | 唯一路径、日期、SHA-256和双链通过 |
| `G3 screening_built` | 02完成筛选、最终日报与合格派生构建 | registry、来源链、Manifest和批次一致；不存在阻断状态 |
| `G4 state_disposition` | 确定03去向；需要时形成待确认状态／情绪快照 | 去向、模式、截止点、选项、来源及用户自填／显式未知状态得到确认 |
| `G5 state_registered` | 03正式快照校验并登记 | 文件SHA-256、snapshot_id和登记表一致 |

某日没有合格正式Decision时，G3可以完成，但G4记为`not_eligible`；用户明确本次不进入03时记为`not_requested`。两者都是合法终点，不得为了走完整链而制造Decision或情绪样本。

### 3.1 H1健康层并行状态机

| 状态 | 含义 | 门禁或合法终点 |
|---|---|---|
| `H0 source_checked` | 检查Apple健康导出、数据库日期覆盖和既有报告 | 区分新源、复用、`pending_health_data`或`pending_permission` |
| `H1 ingested` | 新哈希导入；相同哈希跳过；全量包按目标日期筛选 | `imported / reused / pending_health_data / pending_permission` |
| `H2 summary_ready` | 按自然日与D日晚18:00至D+1日12:00睡眠窗口聚合 | 输出日汇总，数据未齐可为`provisional` |
| `H3 base_report_ready` | 生成客观健康Markdown/JSON | 路径、SHA-256、算法版本和覆盖可追溯 |
| `H4 integrated_report_ready` | 将健康报告与G2正式日报及D分析联合，并执行健康、选择与生活关联算法 | 时间方向、证据等级和反证完整；不推断主观状态或因果 |
| `H5 health_registered` | 追加主系统H1日登记 | 登记ID、路径、SHA-256和状态一致 |

H1是非阻塞分支：`pending_health_data`、D+1夜间数据尚未齐全或只有H3基础报告，均不阻止G3—G5继续。资料到齐后从最近的H状态补算，不重跑已验证的G阶段。H4依赖G2；H0—H3可以独立执行。

### 3.2 系统更新状态机

| 状态 | 含义 | 进入下一状态的门禁 |
|---|---|---|
| `U0 evidence_locked` | 锁定资料窗口、现行版本和用户目标 | 证据量满足治理要求，事实与建议分离 |
| `U1 change_set_defined` | 确定更新级别、受影响文件、假设、风险与依赖顺序 | 权威来源和回滚对象明确 |
| `U2 recovery_verified` | 创建更新前ZIP、逐文件清单和SHA-256 | 包内条目全部可读且哈希一致 |
| `U3 template_validated` | 先完成模板／Schema候选及配套分析规则 | 空白性、字段所有权、结构和引用通过验证 |
| `U4 skill_validated` | 再更新总调度或组件Skill | Skill校验、停止条件和交接契约通过 |
| `U5 release_synced` | 同步入口、模块说明、档案和回滚说明 | 现行版本唯一，旧版退出运行目录 |
| `U6 audit_passed` | 完成链接、版本、哈希及历史边界审计 | 无活动链接指向已退役运行文件；恢复包可解压并逐项复核 |

用户指定“先模板、后Skill”时，U3和U4不得并行或倒序；模板候选验证失败时不得开始Skill更新。具体文件级步骤以[系统更新契约](references/system-update-contract.md)为准。

## 4. 阶段执行

### G0→G2：01原始数据记录

调用[[01.原始数据记录/02_运行资源/skill库/智能体执行Skill|personal-event-system-orchestrator]]。视频、SRT或非结构化日记由其调用`diary-transcription`。

01必须先形成待确认草稿。精力、情绪、压力、动机、内部阻力和自我解释等字段，只有用户明确口述或填写才记录；其他情况保持模板规定的空白。用户确认、正式归档和D分析门禁通过后，01向本总调度返回日期、正式提交路径与SHA-256、D分析路径与SHA-256、覆盖状态、时序状态和形成方式。

日级完整流程中，01到达R2正式日提交后，总调度可以先运行H0—H3，再让01按AI规则v17生成R3日分析：健康报告可用时写紧凑摘要及固定关联节，不可用时在两处写`pending_health_data`。R3完成后形成G2，随后才运行H4联合报告和H5登记。这个插入点不改变01原始事实，也不把H分支变成G主链阻断条件。

遇到日期冲突时，上述顺序在G0后暂停；候选模板可以记录文件日期和用户日期，但不得写正式日期字段。用户确认日期后从候选模板恢复，不重新转写。

使用v14模板时，`报告形成方式`由执行流程写入；只有本人选择建立正式行动桥且必需字段齐全时才生成行动桥ID并跨日原样传递。“仅明日想法”只作为未来计划。用户完成外部工作副本后说“已填写”，只表示该副本可进入确认门禁，不授权改写其主观字段或覆盖同日正式异本。

### G2↔H0→H5：H1健康层

调用[[H1.个人健康层/02_运行资源/personal-health-layer/SKILL|personal-health-layer]]。优先检查已有数据库覆盖和源文件SHA-256；相同导出不得重复导入。健康层完整数据库、导入源和报告保存在`E:/个人事件量化系统/H1.个人健康层/health-runtime/`；主系统H1登记表保存日期、状态、路径、哈希、版本和质量标志；旧根仅作迁移前只读备份。

- 有G2时可以生成日记联合健康报告；没有G2时最多推进至H3。
- 完整导出按目标日期过滤；历史日期只有在用户明确要求补算、或登记状态已经是`source_changed`时才重生成。
- 日期D的夜间睡眠等待D+1中午窗口结束后再定稿；此前可登记`provisional`。
- 少于14个同源有效日只做观察；14日初始范围，28日滚动基线。
- 关联分析先按真实时间判断健康在前、生活／选择在前或仅共现；至少3次可比同向观测才形成重复候选，任何等级都不自动表示因果。
- 健康缺失或健康目录不可写分别返回`pending_health_data`或`pending_permission`，不要求用户逐项手填，也不阻断G3—G5。
- 健康数据只在样本窗口早于选择点截止时间时向03提供客观情境；不能代填精力、压力、困倦、疼痛、情绪、动机或启动阻力。

### G2→G3：02数据筛查

调用[[02.数据筛查/06_程序与Skill/技能库/daily-decision-training-pipeline/SKILL|daily-decision-training-pipeline]]。总调度只传递01正式提交、同日D分析、日期、哈希和质量边界；字幕、草稿、桌面副本和主观推测不得直接进入02。

`waiting_for_analysis`、`source_changed`、重复源或同日最终报告冲突必须停止。02返回正式Decision、粗粒度记录、未决提及、任务、最终报告路径与哈希、执行版本、构建批次和研究资格。

### G3→G5：03状态与情绪量化

仅对02正式Decision调用[[03.个人状态量化/06_程序与Skill/技能库/decision-state-snapshot/SKILL|decision-state-snapshot]]。每次只处理一个明确选择点。

- 结果已经发生：使用`retrospective_reconstruction`，严格回测资格固定为否。
- 结果尚未发生：可以建立`locked_prediction`类型的状态快照，但03仍不生成预测概率。
- 精力、压力、困倦、疼痛、情绪、动机和启动阻力优先由用户在对应时点填写；AI只能整理明确原话，不能根据实际选择或后续行为倒推。
- 日报中的全天情绪不能自动代表某个选择点的截止点前情绪；时间边界无法证明时使用`unknown/null`并进入待确认。
- v14的03处理方式控制去向：`愿意回忆／填写`可用合格字段预填草稿；`无法回忆，登记为未知`生成显式未知草稿并等待确认；`本次不进入03`返回`not_requested`且不建草稿；`尚未决定`或未选返回`needs_user_state`并暂停。任何分支都不得从第1节全天状态补齐选择点状态。
- v14新增可比性门禁：任务完成度只接受用户明示或外部边界；工具／资源依赖与内部阻力分层；反思、未来计划和正式决策分开计数；行动桥必须保持单一对象。

需要登记的03对象先写待确认草稿。只有用户确认和Schema校验通过后，才能写入正式快照并登记；`not_requested`、`not_eligible`和`needs_user_state`不伪造草稿。

## 5. 跨层停止条件

出现以下任一情况，停止跨层推进并保留已通过阶段：

- 日期、同日异本、源文件哈希或现行版本无法裁决；
- 01草稿尚未由用户确认，或正式日提交／D分析不完整；
- 02登记状态阻断、来源已变化、最终报告冲突或构建未验收；
- 02没有正式Decision，或03的选择点、截止点、互斥选项不成立；
- 用户选择愿意填写但尚未确认状态／情绪字段，或03处理方式尚未决定；
- 行动桥ID、来源日期或目标日期与跨日报告冲突，导致当前闭环对象无法唯一确定；
- 目标正式文件或同ID登记存在不同内容；
- 用户填写副本与正式副本的日期或哈希不一致；
- 用户请求只授权当前阶段，或下一阶段尚未启用。

健康层缺失、暂定、等待夜间数据或等待目录权限不属于以上主链停止条件。它只停止H分支，并在全局回执中给出可回填条件。

合法暂停不是失败。返回停止位置、已验证产物、缺少的信息和可继续条件，不重做已完成阶段。

## 6. 全局回执

每个日期返回统一阶段状态：`completed / reused / waiting_user / blocked / not_eligible / not_requested`。

```text
执行日期：
任务终点：G2 / G3 / G5
G0 输入识别：状态｜来源
G1 原始草稿：状态｜路径
G2 正式日报与D分析：状态｜路径｜SHA-256
G3 数据筛查：状态｜最终日报｜build_batch_id或阻断原因
G4 状态／情绪草稿：状态｜snapshot_id｜需要用户填写项
G5 正式状态登记：状态｜路径｜SHA-256
H0 健康来源检查：状态｜来源SHA-256
H1 健康导入：状态｜批次
H2 健康日汇总：状态｜路径｜SHA-256
H3 基础健康报告：状态｜路径｜SHA-256
H4 日记联合健康报告：状态｜路径｜SHA-256
H5 健康登记：状态｜登记ID｜基线状态
关联分析：状态｜规则版本｜候选数｜最高证据等级
运行时：Python版本｜PowerShell或pwsh版本｜权限状态
未修改：受保护的原始材料、上游事实和未授权层
```

只有用户要求的终点达到对应完成门禁时，才报告本次任务完成；不能用G2或G3冒充G5，也不能用文件存在代替哈希、登记和用户确认。

系统更新任务改用U0—U6回执：报告证据窗口、模板版本、Skill版本、恢复包路径与SHA-256、旧版归档、入口同步和最终审计结果；只完成模板候选时不得表示整个更新批次完成。

## 7. 全局不变量

- 跨层只传递明确契约字段、来源路径、对象ID、SHA-256、版本和不确定性。
- 健康数据库和逐样本报告保留在`E:/个人事件量化系统/H1.个人健康层/health-runtime/`；`E:/个人健康层/`是迁移前只读备份，不再同步更新；主系统登记表保留最小索引和来源哈希。
- 下游不得回写上游事实；AI分析和研究解释不得升级为用户事实。
- 用户在最终补充确认段明确纠正同一对象状态时，按最新确认进入正式归档和交接；早期表述保留为冲突证据，不得静默删除。
- 主观状态／情绪缺失时按用户声明的03处理方式执行：等待填写、显式未知或本次不进入；不自动补全、不写人格或因果结论。
- 历史重建、实时状态和严格预测永久分轨。
- 04及以后阶段未正式启用前，不生成预测概率、Outcome评分或模型升级结果。
- 子系统Skill不得绕过本总调度自动跨层。
- 系统更新与日报生产分轨；模板、规则、Skill、入口和档案必须在同一更新批次中保持可恢复、可追溯和唯一现行版本。
- 新健康导出不得静默改写已登记历史日报；历史补算必须产生新的来源哈希和登记审计。
