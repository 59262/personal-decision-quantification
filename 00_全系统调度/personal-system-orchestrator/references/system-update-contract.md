# 全系统更新契约

本参考用于模板、分析规则、Skill和入口的同批更新。具体判断仍服从受影响子系统的版本治理文件；本契约只规定跨文件顺序、恢复与发布门禁。

## 1. U0—U1：锁定证据与改动集

1. 明确实际资料窗口、应有／实有记录数、现行版本和用户要求的顺序。
2. 把重复摩擦、事实错误、用户偏好和模型假设分开；单次异常不能升级为稳定个人结论。
3. 按治理规则确定更新级别、权威来源、受影响文件、兼容风险和回滚对象。
4. 同批依赖冻结：模板字段先定稿，分析规则再适配，Skill只引用已验证契约，入口和档案最后同步。

## 2. U2：恢复包

1. 在任何现行文件修改前，列出本批所有可能受影响文件。
2. 创建ZIP和包内`manifest_sha256.csv`，记录原相对路径、字节数和SHA-256。
3. 重新解压到临时目录，逐项验证文件存在、可读且哈希一致；失败则停止更新。
4. 另存即将退役模板、规则和Skill的可读版本目录。恢复包与可读归档都不得参与现行执行。

## 3. U3：先更新模板

1. 由前一版复制候选文件，升级版本号和生效日期，不在母版中填入任何真实日报值。
2. 只修改跨样本重复出现的字段摩擦；保持不受影响的章节和D／W／M边界稳定。
3. 同步分析规则对新字段的证据权限、冲突门禁和下游交接，不让AI获得新的主观推断权限。
4. 验证：YAML、必需章节、空白复选框、Obsidian链接、用户字段所有权、版本互引和历史兼容说明。
5. 任一验证失败时停在U3，不开始Skill更新。

## 4. U4：再更新Skill

1. 只在U3通过后调整总调度或必要组件；不在多个Skill复制同一套业务规则。
2. 主Skill保留路由、状态机、停点、回执和全局不变量；长契约下沉到`references/`。
3. 更新跨层字段时同步阶段交接契约，并明确缺失值、来源时点和禁止倒推边界。
4. 对每个变更Skill运行结构校验；失败则保留模板候选，但本批不得发布为完整完成。

## 5. U5—U6：发布与审计

1. 同步全系统入口、子系统入口、模块说明、符号规范和必要组件链接。
2. 在演化档案记录证据窗口、问题、改动、版本、恢复包SHA-256、旧版位置、验证结果和回滚步骤。
3. 新版通过后移出运行目录中的前一版；历史日报和历史分析保留原版本双链，不批量改写证据。
4. 全局搜索活动区域中的旧版本引用、断链、双重现行版本和错误状态；档案及历史数据中的旧版本记录不算冲突。
5. 重新计算新版与恢复包SHA-256，输出U0—U6回执。只有U6通过才能宣布整批完成。

## 6. 回滚

若发布后发现结构、链接或运行门禁错误：

1. 停止生成使用新版本的新数据；
2. 用已验证ZIP或可读归档恢复原路径；
3. 恢复入口登记的旧版本和状态；
4. 记录失败批次、已产生数据范围和是否需要迁移；
5. 在重新验证前，不混用新旧模板或Skill。
